# Research Log: Minimalist Auto Clicker UI

## Automation tooling for high-frequency clicking + global hotkeys

- **Decision**: Run the mouse controller in the Electron main process using `@nut-tree/nut-js` for firing clicks and `node-ffi-napi` hooks plus `iohook` for the Alt+C/Escape shortcuts. The renderer sends IPC messages whenever the user updates `ClickSessionConfiguration`, and the main process keeps an in-memory session that stops clicking when motion is detected via repeated pointer polling or `iohook` motion events.
- **Rationale**: `@nut-tree/nut-js` is actively maintained, Promises-based, and supports precise button control across Windows, macOS, and Linux—necessary for the 1–1000 CPS requirement. `iohook` is widely used for global shortcut detection inside Electron and combines well with the same build pipeline, letting us keep the renderer lightweight while guaranteeing the needed hotkeys work even if the UI loses focus. The combination covers the spec’s needs for stationary-start, run-duration, and Escape cancellation without dropping into nightly native modules.
- **Alternatives considered**: `robotjs` has been popular but is no longer maintained and has known build issues on recent macOS/Apple Silicon, making deterministic releases hard. Writing native C++ add-ons would give more control but add significant maintenance burden. Using pure Node Automation APIs (e.g., `node-hid`) would require re-implementing global shortcut detection and stationary logic, which would duplicate effort.

## Deterministic release pipeline for Electron artifacts

- **Decision**: Use GitHub Actions with pinned Node/Electron versions, `npm ci`, and `electron-builder` configured with fixed `artifactName`/`appId` plus reproducible build flags. Each release job will compute SHA256 checksums of the generated installers/zips and publish them alongside a `REPRO.md` guide describing how to run `npm ci`, `npm run build`, and `electron-builder --config`. A `verification.sh` script in the repo will hash the locally produced artifacts so community members can compare.
- **Rationale**: `electron-builder` already supports reproducible builds when dependency versions are pinned and the environment is well-defined. GitHub Actions gives us a consistent runner, `actions/setup-node` ensures the same Node/Electron versions, and `npm ci` enforces lockfile fidelity. The published checksum plus documentation lets auditors independently confirm that the zipped artifacts match the repository state, satisfying the requirement for deterministic GitHub Actions releases.
- **Alternatives considered**: Using `electron-forge` or `nx/electron` would complicate the CI configuration for deterministic builds and lacks the same maturity around reproducibility; rolling our own packaging workflow (custom tarball) would delay release automation. Relying on third-party continuous delivery services would make it harder to publish reproducible checksums integrated with the repo.
